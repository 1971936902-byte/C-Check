适用版本：C-Check `v0.1.0-rc.13`，Linux amd64，Ubuntu 24.04，单张 RTX 5880 Ada 48GB。

## 1. 先理解“一键安装”的范围

“一键”指在宿主机前置条件准备好、完整包验签成功、外置配置确认后，用一条 `install` 命令部署项目。它不是一条命令改造任意共享服务器。

| 工作 | 谁来完成 | 注意事项 |
| --- | --- | --- |
| 确认硬件、空闲资源、管理员权限、安装窗口 | 管理员 | 不占用别人的 GPU 任务，不擅自重启服务器 |
| 安装/维护 NVIDIA 驱动 | 管理员 | 当前驱动可用时不为本项目升级 |
| 安装 Docker Engine、Compose 插件 | 管理员 | 已有可用环境优先复用，不卸载重装 |
| 配置 NVIDIA Container Toolkit | 管理员 | 可能需要重启全局 Docker，必须安排窗口 |
| 准备系统 Python、OpenSSL、curl、tar | 管理员 | 与 Conda base 环境分开 |
| 取得完整安装包并核对发布者身份 | 部署人员 | 不能直接运行未验证的网络脚本 |
| 确认模型路径、许可、文件完整性 | 部署人员/公司授权负责人 | 文件夹名称正确不代表版本正确 |
| 导入项目镜像、生成 Compose 配置和项目网络 | 安装器 | 使用独立项目名，不执行全局清理 |
| 初始化数据库、创建随机凭据、启动服务 | 安装器 | 不预置 `admin/admin` |
| 检查模型、图谱、RAG、报告导出并运行小任务 | 安装器 | 显示 READY 才算安装验收完成 |
| 配置公司网络防火墙、TLS、DNS、VPN、端口映射 | 管理员 | 不属于安装器自动操作范围 |

安装器不会在宿主 Conda 中安装 PyTorch/vLLM，不升级驱动，不自动安装 Docker，不重启共享 Docker，不杀其他人的 GPU 进程，也不执行 `docker system prune`。

## 2. 当前适配方案与验证边界

宿主机 `nvidia-smi` 显示 CUDA 13.0，表示驱动支持能力，不表示项目必须安装 CUDA 13 Toolkit。当前包内部使用 CUDA 12.4 对应运行库，不需要在宿主机另装一套 CUDA Toolkit 来“对齐显示版本”。新驱动向后兼容旧 CUDA 应用的原则见 [NVIDIA CUDA 兼容说明](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)，最终以容器 CUDA 和实际模型验收为准。

本版本已通过源码版/编译版行为对照、38 项 Linux 部署测试、41 项前端测试、镜像分层源码残留检查，以及真实模型文件离线复用验证。此前运行方案在 A100、RTX 4090 Ada 48GB 上有小任务验收记录；这些不能替代你的 RTX 5880 实机验收，也不代表长期稳定性、吞吐或漏洞准确率保证。

## 3. 资源与授权准备清单

### 3.1 资源规划

| 资源 | 准备要求 |
| --- | --- |
| 系统 | Ubuntu 24.04 amd64；不是 ARM，不是在 Windows 上直接运行此 Linux 包 |
| 显卡 | RTX 5880 Ada 48GB，选定卡上没有其他计算任务 |
| CPU | 建议 16 逻辑 CPU 或以上；当前 Qwen 容器配置 8 CPU 配额，少于 8 逻辑 CPU 的主机需另行评估适配 |
| 系统 RAM | 建议 64GB 或以上并给其他项目留余量；48GB 曾有相近环境验证，但不能据此保证共享机器内存充足 |
| 磁盘 | 在模型已存在的基础上，建议相关文件系统仍有 100GB 以上空闲，并额外规划备份、报告增长 |
| 文件系统 | 检查实际挂载点和 inode；不要用其他项目目录或符号链接作为实例目录 |
| 权限 | 需要获准使用 sudo/rootful Docker；rootless 不在本次验收范围 |
| 网络 | 联网获取 Release 或提前传入完整包；主机软件安装需要官方仓库或公司批准的内部镜像源 |
| 时间窗口 | 安装、模型加载、哈希校验会消耗 CPU、内存、磁盘 I/O；先协调共享主机使用人 |

1TB 是总容量，不是剩余空间。Docker 镜像导入需要解压空间，安装器还会缓存一份发布包。已有模型若不能硬链接，可能再复制约 37.4GB。预检中的“至少 12GiB”只是初步门槛，绝不是完整安装所需总空间。

容器有 CPU、内存、PID 和日志轮转限制，但这些上限不是资源预留，也不是“完全不影响别人”的保证。所有容器内存上限相加接近 44GiB，实际峰值须现场观察，不能把宿主机 RAM 全部分配给本项目。

### 3.2 许可与保密

- 公司负责人应核对模型及组件的使用许可，特别是 Jina 的 CC-BY-NC-4.0 条款；本手册不是法律授权意见。
- 配置中的 `evaluation` 或 `authorized` 只是部署声明，不授予使用许可。
- 不把业务 C 源码、模型文件、数据库备份、密码或令牌上传 GitHub。
- 二进制提高直接阅读核心源码的门槛，但无法防止 root/Docker 管理员复制镜像或逆向。
- 当前 GitHub 仓库是公开仓库，既有源代码历史不会因发布二进制而消失。
- 不把 Docker socket 挂载到不受信容器，不使用 `chmod 666 /var/run/docker.sock`。Docker 组本身具有接近 root 的权限，见 [Docker 权限说明](https://docs.docker.com/engine/install/linux-postinstall/)。

### 5.2 Docker Engine 和 Compose

优先按 [Docker 官方 Ubuntu 安装文档](https://docs.docker.com/engine/install/ubuntu/) 或公司批准的软件源准备。不要直接复制官方文档中的“卸载冲突包”步骤到共享服务器；已有部署的主机须先分析依赖关系。

以下只适用于管理员确认“没有需保留的现有 Docker 安装”的主机。建立官方软件源时不使用 `curl | sh`：

```bash
(
set -eu
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /tmp/c-check-docker-key.asc
sudo install -m 0644 /tmp/c-check-docker-key.asc /etc/apt/keyrings/docker.asc
. /etc/os-release
printf 'deb [arch=%s signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu %s stable\n' \
  "$(dpkg --print-architecture)" "$VERSION_CODENAME" | \
  sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
apt-cache policy docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo apt-get --simulate install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
)
```

确认软件源签名、安装计划及公司版本策略后，安装审批过的版本；下面不指定版本号的命令会选软件源候选版本，不代表该候选版本已经过本项目实测：

```bash
sudo apt-get install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker version
sudo docker compose version
```

宿主组件版本由管理员批准并记录；发布包内镜像和 Python 依赖则由签名清单固定。不要把“容器版本已锁定”理解为“宿主 Docker、驱动也被安装器锁定”。不要用缺失 Compose v2 的旧版 `docker-compose` 替代本项目使用的 `docker compose`。

### 5.3 NVIDIA 驱动与容器运行时

如果 `nvidia-smi` 已正常显示 RTX 5880 和当前驱动，先保留驱动。不要盲目下载 `.run` 安装包覆盖系统驱动，也不需要为了容器另装完整宿主 CUDA Toolkit。

先检查 Toolkit：

```bash
command -v nvidia-ctk
```

缺少时，由管理员按 [NVIDIA 官方安装说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html) 配置稳定软件源，不启用 experimental。以下为 apt 系统示例，先下载文件再检查退出状态，下载失败不得继续：

```bash
(
set -eu

gpg --show-keys /tmp/c-check-nvidia-key.asc
sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg /tmp/c-check-nvidia-key.asc

  -o /tmp/c-check-nvidia-toolkit.list
sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \

```

上述 keyring/source 文件已经存在时先核查，不直接覆盖或强制应答 gpg 提示。管理员确认安装计划与版本后执行安装。

```bash
sudo apt-get install nvidia-container-toolkit
```

**下面是宿主机全局变更，只能在批准的维护窗口执行，不是每次部署都要执行：**

1. 记录现有容器和 Docker 配置；如有 `/etc/docker/daemon.json`，先保留带时间戳的备份。配置可能含代理等敏感信息，备份仅限管理员读取，不公开分享。
2. 与其他项目负责人确认停机和恢复安排。
3. 需要时执行以下配置及重启；已经配置成功的主机跳过。

```bash
(
set -eu
HOST_BACKUP=/home/lyh/c-check-host-backup-$(date +%Y%m%d-%H%M%S)
sudo install -d -m 700 "$HOST_BACKUP"
if sudo test -f /etc/docker/daemon.json; then
```

修改后检查原有项目是否恢复。NVIDIA 官方还提示部分 systemd/cgroup 场景存在 daemon reload 后容器丢失 GPU 访问的问题；共享机不要把全局 reload/restart 当作日常排障的第一步。

### 5.4 不能联网的主机

## 6. 阶段 C：取得并验证完整安装包

### 6.1 大小、格式和信任基准

发布包总计约 5.24GB，不含模型；镜像已 gzip 压缩并分片，最大分片 1.5GiB。GitHub Release 单文件须小于 2GiB、最多 1000 个附件，没有 Release 总大小和带宽配额限制，见 [GitHub 官方说明](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas)。本版本 16 个下载附件符合限制。

不要下载 GitHub 自动生成的 `Source code.zip` 充当部署包。也不要只下载 16 个文件后全部平铺在同一目录就直接安装；完整包需要解开引导内容，并将镜像分片放在正确路径。推荐用签名验证后的 `fetch` 自动处理。

通过独立可信渠道确认以下值，不能仅相信同一下载站上的公钥和说明：

### 6.2 联网下载

以下作为普通用户 `lyh` 执行，不使用 sudo 解压。整个括号块遇错停止，不影响父终端的 shell 设置。目录若已有不明文件，先换全新专用目录，不覆盖其他项目。

```bash
(
set -eu
umask 077
BOOT="$HOME/c-check-bootstrap-v0.1.0-rc.13"
BASE=https://github.com/1971936902-byte/C-Check/releases/download/release-v0.1.0-rc.13
mkdir -p "$BOOT"
cd "$BOOT"
for file in publisher.pem release.json release.sig bootstrap.tar.gz; do
  curl -fL --retry 3 "$BASE/$file" -o "$file"
done
printf '%s  publisher.pem\n' 9d1e2a1fe9de3b4245f3abaaa72ccc8ef19e8322e0bc7a3de878353561d86e37 | sha256sum -c -
printf '%s  release.json\n' 3a8a8ab749562905ea53d6d126fa80f818e228e5de699017f4b7890259f9cb56 | sha256sum -c -
openssl pkeyutl -verify -pubin -inkey publisher.pem -rawin -in release.json -sigfile release.sig
/usr/bin/python3 - <<'PY'
import hashlib, json
from pathlib import Path
m = json.loads(Path('release.json').read_text())
p = Path('bootstrap.tar.gz')
assert m['version'] == 'v0.1.0-rc.13'
assert m['tag'] == 'release-v0.1.0-rc.13'
assert p.stat().st_size == m['bootstrap']['size']
assert hashlib.sha256(p.read_bytes()).hexdigest() == m['bootstrap']['sha256']
print('bootstrap verified')
PY
tar -xzf bootstrap.tar.gz
/usr/bin/python3 cli/ccheck.pyz fetch \
  --version v0.1.0-rc.13 \
  --base-url https://github.com/1971936902-byte/C-Check/releases/download \
  --destination "$HOME/c-check-packages" --trusted-key "$BOOT/publisher.pem"
)
```

成功应显示 `Signature Verified Successfully`、`bootstrap verified`，最后显示 `FETCHED v0.1.0-rc.13 ...`。网络中断时可以重跑同版本、同目标目录的 fetch；已完整文件会校验复用，部分文件按协议尝试续传，不保证每个网络代理都支持 Range。

`c-check-bootstrap-...` 与 `c-check-packages` 是不同目录。不要把非空引导目录作为 fetch 的版本目标，不删除 `.fetch-owner.json` 来绕过所有权检查。

```bash
cd "$PKG"
printf '%s  publisher.pem\n' 9d1e2a1fe9de3b4245f3abaaa72ccc8ef19e8322e0bc7a3de878353561d86e37 | sha256sum -c -
printf '%s  release.json\n' 3a8a8ab749562905ea53d6d126fa80f818e228e5de699017f4b7890259f9cb56 | sha256sum -c -
openssl pkeyutl -verify -pubin -inkey publisher.pem -rawin -in release.json -sigfile release.sig
)
```

建立 root 管理的信任文件。已有不同指纹的信任文件不得直接覆盖：

```bash
if sudo test -f /etc/c-check/publisher.pem; then
  printf '%s  /etc/c-check/publisher.pem\n' 9d1e2a1fe9de3b4245f3abaaa72ccc8ef19e8322e0bc7a3de878353561d86e37 | sudo sha256sum -c -
else
  sudo install -D -m 600 "$PKG/publisher.pem" /etc/c-check/publisher.pem
fi
```

上述校验失败不要继续。尤其通过 SFTP 传入完整包时，签名只证明清单可信，不证明目录里的 CLI 尚未被改动。先用系统 Python 对照已验签清单校验 CLI 本身，不导入或执行包内任何代码：

```bash
/usr/bin/python3 - "$PKG" <<'PY'
import hashlib, json, sys
from pathlib import Path
root = Path(sys.argv[1])
m = json.loads((root / 'release.json').read_text())
assert m['version'] == 'v0.1.0-rc.13'
p = root / 'cli/ccheck.pyz'
assert p.is_file() and not p.is_symlink()
assert p.stat().st_size == m['artifact_sizes']['cli/ccheck.pyz']
assert hashlib.sha256(p.read_bytes()).hexdigest() == m['files']['cli/ccheck.pyz']
print('DEPLOYMENT CLI VERIFIED')
PY
```

成功后才能执行 CLI，核对全部载荷：

```bash
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" package-verify \
  --release "$PKG" --trusted-key /etc/c-check/publisher.pem
```

成功输出 `VERIFIED v0.1.0-rc.13 ...`。不要用 `chmod -R 777` 解决校验或权限问题。

### 7.2 外置配置

只在 `$SITE` 尚不存在时复制示例。已有配置先阅读并备份，不能覆盖一个现有实例的配置：

```bash
test ! -e "$SITE" && cp "$PKG/site-rtx5880.example.json" "$SITE"
chmod 600 "$SITE"
/usr/bin/python3 -m json.tool "$SITE"
```

应检查以下关键值：

```json
{
  "instance": "rtx5880-review",
  "data_dir": "/home/lyh/c-check-instance",
  "engine": "docker",
  "profile": "ada-48g-fp8",
  "gpu": "0",
  "runtime_source": "image",
  "model_paths": {
    "qwen": "/home/lyh/models/Qwen2.5-Coder-32B-Instruct-FP8",
    "jina": "/home/lyh/models/jina-code-embeddings-1.5b"

```

- 这是完整 JSON；注释、尾逗号、重复键均不应写入。
- `data_dir` 必须是专用实例目录，不能指向模型目录、用户主目录或其他项目，不要提前建成符号链接。
- `gpu` 为目标卡编号，也可按 CLI 支持的格式选择 GPU UUID。重启后编号可能变化，要重新核对。
- 保持 `runtime_source=image`，使用固定镜像，不要切换为 build 再从公网重新安装 Torch。
- `model_download_policy=offline` 只约束模型；获取 Release 和宿主依赖是另一步。
- 安装后日常命令读取实例保存的配置。不要靠手改外置 JSON 变更现有实例端口；使用 `publish`。
- 不修改 `$PKG` 内示例、脚本、模型清单或其他签名文件，否则全文件校验失败。

### 7.3 检查已有模型

```bash
ls -ld /home/lyh/models/Qwen2.5-Coder-32B-Instruct-FP8
ls -ld /home/lyh/models/jina-code-embeddings-1.5b
du -sh /home/lyh/models/Qwen2.5-Coder-32B-Instruct-FP8
du -sh /home/lyh/models/jina-code-embeddings-1.5b
find /home/lyh/models/Qwen2.5-Coder-32B-Instruct-FP8 -maxdepth 2 -type l -print
find /home/lyh/models/jina-code-embeddings-1.5b -maxdepth 2 -type l -print
```

必须下载完成，不是只有文件夹、下载日志或未完成的分片。清单还要求 config、tokenizer、README、许可/元数据等对应文件；Jina 有 `1_Pooling/config.json`，不能把子目录拍平成同名文件。符号链接形式的缓存需要额外评估，不能当普通完整目录直接保证兼容。

本版本 Qwen 使用 `okwinds/Qwen2.5-Coder-32B-Instruct-FP8` 对应签名文件集合，Jina 具体来源/版本以 `models/model-manifest.json` 为准。同名模型的其他量化方式或其他发布者版本不能直接替换。

需要提前做真正的离线文件校验时，在上面的包校验成功后运行：

```bash
sudo /usr/bin/python3 - "$PKG" "$SITE" <<'PY'
import sys
from pathlib import Path
package = Path(sys.argv[1])
sys.path.insert(0, str(package / 'cli/ccheck.pyz'))
from ccheck.core import load_site, verify_release
from ccheck.models import validate_offline_models
release = verify_release(package, Path('/etc/c-check/publisher.pem'))
site = load_site(Path(sys.argv[2]))
assert site.get('model_download_policy') == 'offline'
validate_offline_models(release, site)
print('OFFLINE MODEL CHECK PASSED; no instance or GPU workload was created')
PY
```

它会读取约 37.4GB 权重计算哈希，耗时与磁盘有关；不是 GPU 推理，也不是死锁。正式 install 还会重新校验，不能因为第一次校验成功就修改原模型。

离线不匹配时会指出 `qwen/文件名` 或 `jina/文件名`。先核对下载来源、大小和清单 SHA256，不删除已有权重，不把 offline 改成 online 碰运气，也不手改签名清单来跳过校验。

同一文件系统且源文件对容器用户可读时可硬链接；私有 0600 文件或跨文件系统会复制。安装器不会通过 chmod/chown 原模型文件来获得权限。硬链接意味着两条路径指向同一文件内容，模型目录应作为不可变缓存管理，禁止原地编辑；需要换模型时用新目录和受控迁移。

### 7.4 宿主预检与容器 GPU 检查

```bash
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" doctor --config "$SITE"
```

`doctor` 是只读宿主前提检查，不创建容器，不下载模型，也不替代上一节模型哈希校验或真正 CUDA 推理测试。

如需在正式安装前单独验证 Docker GPU 访问，可以先从已验证包只导入 Qwen 镜像，再运行只读测试。此操作会占 Docker 磁盘，但不加载模型、不启动项目栈。先确认指定 GPU 没有他人任务。

```bash
(
set -eu
cd "$PKG"
cat images/qwen.tar.gz.part0000 images/qwen.tar.gz.part0001 images/qwen.tar.gz.part0002 | sudo docker image load
QWEN_IMAGE=$(/usr/bin/python3 -c 'import json;print(json.load(open("release.json"))["images"]["qwen"]["id"])')
sudo docker run --rm --gpus 'device=0' --network none --read-only \
  --tmpfs /tmp:rw,exec,mode=1777 -e HOME=/tmp --entrypoint python "$QWEN_IMAGE" -c \
  'import torch; assert torch.cuda.is_available(); x=torch.ones(1,device="cuda"); print(torch.__version__,torch.version.cuda,torch.cuda.get_device_name(0),x.item())'
)
```

正确输出应包含项目锁定的 Torch/CUDA 版本和 RTX 5880 名称。这比单看 `nvidia-smi` 更接近真实容器使用，但仍不替代完整模型加载和 install 验收。若某 Docker 版本导入后映射了不同镜像 ID，不要改签名清单；停止这个可选步骤，保留输出，由发布者评估。正式安装器有独立的镜像身份校验机制。

不要为此额外拉取“latest” CUDA 镜像。正式安装会复用身份一致的已导入镜像，不再重复导入。

## 8. 阶段 E：执行一键安装

安装前最后确认：包验签成功、外置配置正确、模型校验通过、GPU 空闲、端口空闲、磁盘有余量、共享机维护安排已确认。

建议在 MobaXterm 保持连接，或使用已安装的 tmux。不要启动两个安装进程；使用 tmux 时，断线后先重新 attach 原会话，不要立即重新下发安装。

```bash
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" install \
  --config "$SITE" --release "$PKG" \
  --trusted-key /etc/c-check/publisher.pem --version v0.1.0-rc.13
```

预期阶段顺序：

1. 验签、全文件校验、模型离线预检、空间检查。
2. 创建专用目录、权限、随机凭据，缓存签名包。
3. 导入/校验镜像，准备专用模型路径。
4. 生成项目 Compose 配置及内部网络。
5. 启动 MySQL、Redis、Qdrant，检查应用到数据服务的连接并初始化数据库。
6. 检查 GPU 计算任务和显存，再启动 Qwen 与 CPU embedding。
7. 启动 API、worker、前端，并注册真实默认模型。
8. 创建验收任务、检查审查结果、跨文件调用图、RAG 索引、Markdown/PDF 导出、模型指标和 GPU 遥测。
9. 保存部署状态，输出 `READY local application verified`。

验收会留下一个 `Release-v0.1.0-rc.13-acceptance` 测试任务，是有意的，不是误下发。目标样例应只报告 `protocol.c` 第 7 行一项问题；严格结果不符会停止验收，而不是只凭模型健康就宣布成功。

安装没有固定完成分钟数：模型哈希、镜像导入、CPU 模型加载、首次 GPU 初始化均会耗时。没有 READY 不算成功，但看到进度暂时不动也不能立即认定阻塞；先看当前阶段、日志、PID 和磁盘/GPU 活动。

失败通常保留已准备的文件与容器用于排查，不保证自动清空或恢复到从未安装的状态。尤其 GPU 占用检查在模型启动前执行，此时数据库等可能已经启动；不要把“拒绝 GPU 启动”理解成此前零变更。

## 9. 阶段 F：首次访问与验收

### 9.1 查看状态与密码

```bash
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" status --config "$SITE"
curl -I http://127.0.0.1:18800/
sudo cat "$DATA/secrets/admin_password"
```

登录用户名是 `admin`，密码以上述专用文件为准。不要在公开屏幕共享、录屏、CI 日志或工单中显示密码，不把它写回示例配置，也不要改成 `admin/admin`。密码文件的权限由安装器管理，普通 `lyh` 账号不能直接读时使用获授权 sudo，不 chmod 放开权限。

### 9.2 默认推荐：SSH 转发

在能连接公司服务器的电脑上执行，或在 MobaXterm 的 Tunneling 中配置等价规则：

```bash
ssh -N -L 127.0.0.1:18800:127.0.0.1:18800 lyh@服务器内网IP
```

浏览器打开 `http://127.0.0.1:18800`。若电脑本地端口冲突，可把第一个 18800 改为 18801，再访问本地 18801；服务器端仍是 18800。服务器 SSH 端口不是 22 时另加 `-p 实际SSH端口`。不要在命令中明文追加密码。

MobaXterm 参数：本地监听 127.0.0.1:18800，SSH 登录用户 lyh，SSH 主机为服务器内网 IP，远端目标 127.0.0.1:18800。本地转发在哪台电脑建立，就在哪台电脑浏览器访问；另一台电脑的 localhost 不是同一地址。

### 9.3 公司局域网开放（可选）

先让管理员确认访问范围、实际服务器地址、端口和防火墙规则，再执行：

```bash
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" publish --config "$SITE" \
  --mode lan --bind 0.0.0.0 --port 18800 \
  --public-url http://实际服务器内网IP:18800
```

把占位地址替换为真实 IPv4 地址，不把 0.0.0.0 当成浏览器访问地址。仅希望指定网卡开放时，可以把 bind 改成该网卡实际地址。`publish` 会排空当前任务并更新容器与保存的配置，不是零中断配置命令。

只允许受信公司网段访问 Web 端口，不额外发布 MySQL、Redis、Qdrant、embedding、vLLM 端口。Docker 发布端口可能绕过普通 UFW 规则，需管理员按实际 Docker 防火墙后端配置，不能认为“UFW 已开”就安全，见 [Docker 防火墙说明](https://docs.docker.com/engine/network/packet-filtering-firewalls/)。

需要公网访问时优先公司 VPN 或已有 HTTPS 反向代理；TLS、DNS、NAT、登录访问控制和证书由管理员配置。本版不自动部署公网 HTTPS，不能把内网 HTTP 口直接映射到公网作为正式使用方案。

### 9.4 安装后人工确认

- 能登录前端，验收任务状态为完成，能打开报告并下载 Markdown/PDF。
- 默认模型正确，资源监控能看到 GPU 显存和 vLLM 指标。空闲时吞吐为零正常，不能要求空闲时持续有 token/s。
- 图谱/RAG 可正常查看，不是降级成仅关键词检索后仍当完整验收通过。
- 向公司代码扫描前先提交一个可公开的小样例，观察报告与耗时，再逐步扩大规模。
- 记录版本、宿主驱动/Docker/Toolkit 版本、验收任务 ID、耗时、显存峰值、RAM/swap 情况。不要把一次小任务成功当长期运行测试。

需要重新生成一个真实验收任务时：

```bash
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" verify --config "$SITE" --fresh
```

此命令不只是查看状态：它会读取模型校验哈希并实际下发验收任务，应安排 GPU 和 worker 时间。不要每分钟执行。

## 10. 目录、隔离和资源管理

```text
/home/lyh/models/                      已有原模型缓存，不是实例目录
/home/lyh/c-check-packages/            下载的完整发布包
/home/lyh/c-check-site.json            外置部署配置
/home/lyh/c-check-instance/
  config/                             生效配置和发布者公钥
  secrets/                            随机凭据，禁止公开
  models/                             实例模型文件，可能硬链接或复制
  releases/                           安装器缓存的签名版本
  data/                               数据库、索引、源码上传、运行缓存等
  state/                              Compose、部署/操作状态、验收报告
  backups/                            加密备份
/etc/c-check/publisher.pem            root 管理的可信公钥
```

原模型文件不会因安装被改权限或重命名。实例目录中的模型有时与缓存硬链接，不应在任一路径原地修改内容。磁盘用量统计还会受到硬链接、文件系统和缓存影响，不能简单把每个 `du` 的结果相加。

服务使用独立 Compose 项目和网络，应用大多以非 root 用户、只读根文件系统运行；数据库等有专用写入目录，密钥通过文件挂载。限制与校验提高隔离程度，但 root/Docker 管理员仍能访问，不等同硬件安全隔离或加密机密计算。

## 11. 常用管理命令

新会话先重新设置 `PKG`、`SITE`、`DATA`，不要对着其他项目目录运行原始 compose 命令。

```bash
# 查看状态和版本
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" status --config "$SITE"
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" version --config "$SITE"

# 诊断指定服务，先限制日志行数
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" logs --config "$SITE" qwen --tail 100
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" logs --config "$SITE" embedding --tail 100
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" logs --config "$SITE" worker --tail 100
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" logs --config "$SITE" api --tail 100

# 排空已有任务后停止本项目，保留数据
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" stop --config "$SITE"

# 检查模型和资源后重新启动
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" start --config "$SITE"
```

`stop` 会先禁止新任务并等待旧任务结束。排空超时时，维护状态可能保留，不会强行杀审查。不要据此删除 maintenance 文件跳过保护，应先查看仍在运行的任务。

容器配置使用 `unless-stopped` 重启策略；Docker 开机启动由管理员管理。重启后 GPU 被其他人先占用时，不能保证模型自动启动成功。手动 stop 后也不要假设重启主机一定会帮你重新启动。

未成功安装、尚无 `state/deployment.json` 时，部分管理命令会拒绝执行。此时先查看安装终端、`state/operation.json`，必要时由管理员只读诊断实例自己的 Compose：

```bash
sudo cat "$DATA/state/operation.json"
sudo docker compose -f "$DATA/state/compose.json" ps -a
sudo docker compose -f "$DATA/state/compose.json" logs --tail 100 qwen
```

文件尚未生成时对应命令报不存在属于阶段信息，不要为了绕过错误自己伪造 deployment.json。

## 12. 备份、升级与卸载

### 12.1 备份准备

有真实代码和报告后应制定备份策略，数据库文件、上传源码和密钥均可能敏感。部署包和模型缓存不是业务备份。

备份密钥必须在实例目录之外、仅管理员可读，并另行离线保管。示例生成命令禁止覆盖已有密钥；先确认以下专用目录没有与其他用途冲突：

```bash
sudo install -d -m 700 /home/lyh/c-check-keys
sudo sh -c 'umask 077; set -C; openssl rand -hex 48 > /home/lyh/c-check-keys/backup.key'
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" backup --config "$SITE" \
  --backup-key /home/lyh/c-check-keys/backup.key
```

备份会排空任务并短暂停止部分服务，不是在线零停机操作。`backup.keep=3` 只保留受本实例识别、验证通过的近期备份；备份前先检查空间并将重要快照另行归档。丢失密钥无法靠重新生成同名文件恢复。

### 12.2 升级与回退

后续版本必须重新验签，使用 `update`，不要用 `install` 静默覆盖不同版本。更新与回退均需要外部 backup-key，并受 schema 与模型清单兼容性约束。更换嵌入模型/向量维度、数据库 schema 或模型文件集合，不属于透明镜像回退范围，须单独制定迁移方案。

本手册不提供可直接复制的未知版本升级命令，避免把占位版本误用于生产。先在独立实例验证新版本，再审批公司数据迁移。

### 12.3 卸载

已成功安装的实例，如确认要移除服务而保留数据：

```bash
sudo /usr/bin/python3 "$PKG/cli/ccheck.pyz" uninstall --config "$SITE"
```

不要附加 `--purge`，除非管理员已经核对实例、完成备份并明确批准永久删除。默认卸载保留实例数据、原模型和其他项目，不是释放所有镜像空间的全局清理。

## 13. 常见失败与正确处理

| 现象 | 优先检查 | 禁止的处理方式 |
| --- | --- | --- |
| Docker 只有 Client、连接 daemon 失败 | sudo 权限、daemon 是否正常、公司 Docker 安装方式 | chmod 666 socket、盲目重装 |
| `could not select device driver` / GPU 容器不可用 | Toolkit、Docker runtime 配置、维护窗口后是否验证 | 为此直接升级所有驱动/重启共享主机 |
| 签名/哈希校验失败 | 公钥指纹、下载完整性、是否改过换行/文件 | 忽略签名、改清单 checksum |
| `offline model missing or differs` | 错误给出的具体文件、来源、分片、子目录、SHA256 | 删除原模型、改 online 自动重下 |
| 权重文件夹存在但仍失败 | 是否只有日志、下载未完成、不同 FP8 发布者版本 | 仅凭目录名认定安装器误判 |
| GPU has active compute workloads | GPU 编号、其他计算任务所有人、预约窗口 | kill 他人进程、降低安全预算硬挤显存 |
| GPU memory below budget / CUDA OOM | free 显存、其他程序、profile、模型是否确为指定 FP8 | 随意改量化/KV/上下文后仍宣称同版已验证 |
| 磁盘不足 | Docker Root Dir、实例磁盘、inode、复制而非硬链接、备份 | docker system prune、删别人目录 |
| embedding 慢或内存紧张 | CPU/RAM、swap、容器日志和 OOMKilled | 只看 GPU 利用率判断它卡死 |
| 无法访问 18800 | 是否仅绑定 localhost、SSH 隧道在哪台电脑、端口冲突 | 直接暴露数据库和 vLLM 到公网 |
| 登录失败 | 用户名 admin、实例内随机密码、是否访问了其他项目端口 | 公开密码、重置数据库、改 admin/admin |
| 任务在某百分比停留 | worker/vLLM 日志、GPU/CPU、当前 task ID、超时策略 | 重复点击提交、反复重启 worker |
| 健康正常但安装没有 READY | 真实验收任务、精确行号/结果、图谱、导出、指标是否失败 | 将 alive/healthy 等同业务验收成功 |
| install 中途断线 | 原终端/tmux、安装进程是否仍活着、operation.json 是否更新 | 未确认就启动第二个安装进程 |
| 同版本重新安装被拒绝 | 版本是否真的同一签名内容、实例所有权、是否已有另一版本 | 改版本号或删除 owner 文件强行绕过 |

排查时先保存时间、执行阶段、错误摘要、版本和任务 ID。日志/配置可能含代码片段、内部路径或凭据，发给别人之前脱敏，不上传完整 `secrets/`、数据库、业务源代码或私钥。
