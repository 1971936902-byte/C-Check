# 方案二：轻量在线发布、部署与版本管理

## 目标和边界

保留方案一（完整离线包及 rc13～rc16 发布），新增独立的 `v0.2.0-rc.1` 在线发布线。
不是重新下载一份大离线包，也不是在宿主机执行 pip install。小包只包含签名部署 CLI、
配置示例、组件锁、许可证、模型清单和验收样例。核心编译产物留在 backend 镜像里，
安装时获取镜像。实际安装体积和首次网络流量不会因为发布包变小而消失。

## 两种方式对照

| 项目 | 方案一：离线完整包 | 方案二：在线轻量包 |
|---|---|---|
| 发行目录镜像分片 | 包含，完整包约 5.23GB | 不包含 |
| 模型权重 | 已由清单另行准备 | 已有则校验复用，缺失时按清单下载 |
| 独立核心 wheel | 包含 | 不包含，核心在 backend 镜像中 |
| PyTorch/vLLM/Python 依赖 | 预装在运行镜像 | 部署时下载同一固定版本镜像 |
| 宿主机 pip/Conda | 不改 | 不改 |
| 网络中断 | 完整准备后可离线 | 首次缺失资源需联网，支持续传/缓存 |
| 升级前资源准备 | 主要来自本地包 | 自动预取，失败不进入维护阶段 |
| 部署/回退 | 原 CLI | 兼容原 CLI，新增 download-plan/prepare-assets |

rc16 的 5.27MB 是依赖旧完整包的补丁，不是首次部署完整体积。本方案的小包可以在没有旧
镜像分片目录时启动下载，但仍需要网络和满足前置条件的宿主机。

## 版本管理机制

1. **应用发布版本**：Git commit、源码清单哈希、Release 版本和 Ed25519 签名绑定。
2. **容器运行环境**：Docker Compose 管理编排；镜像按 OCI digest 拉取并复核文件系统与执行
   配置身份。不使用 latest，不因镜像标签变化而自动升级。
3. **Python 依赖**：保留 backend/qwen/embedding/compiler 的完整版本锁和 wheel SHA256。
   由可信构建端安装到镜像，现场不重新解析版本组合，不把 CUDA 库混进别人 Conda 环境。
4. **模型权重**：仓库、revision、每个文件的长度和 SHA256 锁定，不能仅凭目录名判定正确。
5. **统一入口**：`components.lock.json` 汇总上述镜像、Python 包、模型清单，必须与签名
   release.json 一致。站点文件只能改变路径、来源和运行参数，不能改变锁定版本或哈希。

容器锁定的系统库也由镜像身份约束。主机内核、NVIDIA 驱动、Docker、Compose、Toolkit 属于
管理员准备的主机基础设施，不会为了本项目而自动替换。构建和部署不是同一个阶段；
为了减小包而在每台机器临时解依赖/编译 CUDA，不属于本方案首版支持范围。

## 下载来源和供应链校验

MySQL、Redis、Qdrant：优先使用官方仓库 digest；拉取受限时可回退到原签名清单的 HTTPS
镜像分片。应用/前端/Qwen/Jina CPU 镜像：从已有完整 rc14 Release 获取 SHA256 固定分片，
加载后仍校验镜像身份。GPU Jina 复用 Qwen 镜像，保留 CPU 镜像供回退。

首版没有声称已经把专用镜像发布到 GHCR/Harbor。可在站点配置中指定企业 HTTPS 制品镜像
目录或容器仓库代理；来源变了，摘要不变。迁移到公司镜像仓库可后续做，不必重构部署流程。
不要删除旧发行资源；公司长期部署建议将依赖镜像和分片同步到受控制品库。

## 站点配置

复制发行包 `site-online.example.json` 到包外，按实际环境修改：

- instance/data_dir：新实例和独立数据目录，不能指向其他项目。
- profile/gpu/gpu_access_mode：48GB Ada、GPU 编号/UUID 和 CDI；40GB A100 删除 performance。
- model_paths：已有 Qwen/Jina 目录；仅校验和读取，不改原权重。
- web：本地端口、绑定地址、站点 URL；公网通过现有网关/NAT 单独发布，不自动开放管理端口。
- network_subnets：三个与 LAN/VPN/其他容器不重叠的子网。
- delivery.cache_dir：下载缓存，调用用户拥有且权限 0700；sudo 时由 root 创建专用目录。
- delivery.offline：true 完全禁止缺失资源联网。
- model_download_policy：offline 仅限制模型，仍允许下载镜像。
- delivery.artifact_base_url：可选企业 HTTPS 分片目录，不写入账号口令。
- delivery.registry_mirrors：如 `{"docker.io":"harbor.company.example/dockerhub"}`，保持原 digest。

Docker 仓库凭据用管理员配置的 Docker credential store；密码、签名私钥不能放进配置或发布包。
备份密钥继续外置。管理员密码仍随机初始化，升级不重置。

## 标准安装

先验签 bootstrap 并运行 package-verify。信任锚沿用原 PEM 指纹
`9d1e2a1fe9de3b4245f3abaaa72ccc8ef19e8322e0bc7a3de878353561d86e37`。

下载 Release 附件，不要下载源码 zip 代替发布包。以下目录必须全新，公钥必须是此前独立确认
的信任锚，不能仅信任本次下载的 publisher.pem：

```bash
set -eu
umask 077
PKG=/home/lyh/c-check-packages/release-v0.2.0-rc.1
TRUST=/etc/c-check/publisher.pem
BASE=https://github.com/1971936902-byte/C-Check/releases/download/release-v0.2.0-rc.1
test ! -e "$PKG"
mkdir -p "$PKG"
cd "$PKG"
for file in release.json release.sig bootstrap.tar.gz checksums.sha256; do
  curl -fL --retry 3 "$BASE/$file" -o "$file"
done
printf '%s  %s\n' \
  9d1e2a1fe9de3b4245f3abaaa72ccc8ef19e8322e0bc7a3de878353561d86e37 \
  "$TRUST" | sudo sha256sum -c -
sudo openssl pkeyutl -verify -pubin -inkey "$TRUST" \
  -rawin -in release.json -sigfile release.sig
python3 - <<'PY'
import hashlib,json
from pathlib import Path
m=json.loads(Path('release.json').read_text())
assert m['version']=='v0.2.0-rc.1' and m['distribution']['kind']=='online'
for name in ['bootstrap.tar.gz','checksums.sha256']:
    p=Path(name)
    assert p.stat().st_size==m['artifact_sizes'][name]
    assert hashlib.sha256(p.read_bytes()).hexdigest()==m['files'][name]
print('Signed bootstrap verified')
PY
tar -xzf bootstrap.tar.gz
```

```bash
PKG=/home/lyh/c-check-packages/release-v0.2.0-rc.1
SITE=/home/lyh/c-check-online-site.json
TRUST=/etc/c-check/publisher.pem
sudo python3 "$PKG/cli/ccheck.pyz" package-verify --release "$PKG" --trusted-key "$TRUST"
sudo python3 "$PKG/cli/ccheck.pyz" download-plan --config "$SITE" --release "$PKG" --trusted-key "$TRUST"
sudo python3 "$PKG/cli/ccheck.pyz" prepare-assets --config "$SITE" --release "$PKG" --trusted-key "$TRUST"
sudo python3 "$PKG/cli/ccheck.pyz" network-plan --config "$SITE"
sudo python3 "$PKG/cli/ccheck.pyz" install --config "$SITE" --release "$PKG" --trusted-key "$TRUST"
```

配置完成后，一条 install 可以自动下载、建容器和启动验收；预下载步骤用于提前暴露网络问题。
prepare-assets 不启动业务服务、不占 GPU，也不初始化数据库。
只准备镜像可加 `--images-only`。缓存命中会验证复用，不因重跑安装就重复下载大文件。
模型和分片支持 Range 续传、指数重试、长度及 SHA256 校验；损坏文件不能变成有效缓存。
同一缓存并发准备会被锁拒绝，不进行竞态覆盖。

## 升级和回退

保留方案一完整包和备份。相同模型/数据库 schema 可通过 update 迁移至轻量包；
先验证并下载依赖，随后才排空任务、加密备份及重启本项目服务。
下载失败不先停服务；服务验收失败沿用原配置恢复机制，并可能保留维护状态供人工检查。
更新 delivery 来源配置可修改外置站点文件；其余已有实例参数仍以保存的站点配置为准。
GPU/CPU 切换用显式 --performance-profile shared-gpu 或 cpu-serial，不手改托管 Compose。
回退要使用原签名包/一致性备份，不删除 deployment.json，不使用 down -v 或全局 prune。

## 本次验证范围

构建服务器为 A100 40GB，独立测试实例采用 CPU Jina，未替换原线上数据库。
验证包括 119 项 Linux 工具测试、真实 HTTPS 前端镜像下载/导入、固定模型元数据下载、
28 个本地模型文件 SHA256 校验、缓存复用、新数据库及全服务启动、真实审查和运行时 verify。
这不是空 Docker 缓存下重新下载全部大镜像/权重的测试，也不是 RTX5880 双模型共同驻留测试。
测试实例结束后停用并保留数据，原 C-Check 实例恢复；测试任务不在原实例历史记录中。

## 构建端操作

`deploy/release/build_online_release.py` 从独立可信的完整 rc16 基包生成在线包，不重编应用。
要求原签名身份、已提交冻结源码、匹配源码哈希的测试报告、原锁定模型和镜像身份不变。
应用源码、模型或 Docker 构建输入变化会拒绝轻量重打，必须重新走完整构建和验收。
可在无 GPU 的 Linux 上生成小包；GPU 运行验证必须在相应服务器上进行。

```bash
PYTHONPATH=/opt/c-check-publisher-tools python3 -B deploy/release/build_online_release.py \
  --base-release /opt/c-check-releases/release-v0.1.0-rc.16 \
  --base-source /opt/c-check-release-build-rc16-v4/source \
  --source /绝对路径/已冻结源码 \
  --output /opt/c-check-releases/release-v0.2.0-rc.1 \
  --version v0.2.0-rc.1 \
  --trusted-key /可信公钥/publisher.pem \
  --signing-key /可信环境/外置私钥.pem \
  --yaml-package /opt/c-check-publisher-tools/yaml \
  --validation-report /绝对路径/匹配源码的测试报告.json
```

私钥仅用于可信发布端，绝不进入小包、镜像、部署服务器或 GitHub。后续版本需变更构建器允许
的发布版本并重新测试/签名，不能通过现场改版本号绕过校验。
