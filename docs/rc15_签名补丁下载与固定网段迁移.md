# rc.15 签名补丁下载与固定网段迁移

本补丁只更新部署工具、固定网络与迁移逻辑，7 个镜像、模型清单、运行时配方及核心二进制组件均复用 rc.14。不是重新安装业务数据，也不要求重新下载模型。

## 1. 重要边界

- 新建 rc.15 发布目录，不覆盖 rc.14 包，不手改已签名文件。
- 保留 `/home/lyh/c-check-instance` 及其中的数据库、上传、模型、凭据和状态。
- 不重启 Docker，不改全局网络池，不使用 `docker network prune` 或 `down -v`。
- 默认 data=`172.30.10.0/26`、inference=`172.30.10.64/26`、edge=`172.30.10.128/26`；前两个仍为内部网络。它们是子网，不是固定容器 IP。
- 先执行网络预检，冲突时停止，不能通过跳过检查强制部署。
- 原发布公钥指纹不变：`9d1e2a1fe9de3b4245f3abaaa72ccc8ef19e8322e0bc7a3de878353561d86e37`。

## 2. 增量下载和验签

要求本机保留完整 rc.14 包的 `images/` 目录。以下三个路径按现场实际情况修改；`SITE` 是现有外置站点配置，不是包内示例。

```bash
set -eu
umask 077
OLD=/home/lyh/c-check-packages/release-v0.1.0-rc.14
NEW=/home/lyh/c-check-packages/release-v0.1.0-rc.15
SITE=/home/lyh/c-check-site.json
TRUST=/etc/c-check/publisher.pem
BASE=https://github.com/1971936902-byte/C-Check/releases/download/release-v0.1.0-rc.15
test -d "$OLD/images"
test -f "$SITE"
test ! -e "$NEW"
mkdir -p "$NEW"
cd "$NEW"
for file in release.json release.sig bootstrap.tar.gz checksums.sha256; do
  curl -fL --retry 3 "$BASE/$file" -o "$file"
done
printf '%s  %s\n' \
  9d1e2a1fe9de3b4245f3abaaa72ccc8ef19e8322e0bc7a3de878353561d86e37 \
  "$TRUST" | sudo sha256sum -c -
sudo openssl pkeyutl -verify -pubin -inkey "$TRUST" \
  -rawin -in release.json -sigfile release.sig
```

任何验证失败立即停止。`TRUST` 应是之前已经验证过、由 root 管理的公钥，不能把新下载的公钥直接当作信任锚。若文件不存在，先按 rc.14 安装文档从已独立确认指纹的公钥建立 root-owned 信任锚，不能更换原发布身份。

签名通过后，核验新版引导包和基包身份：

```bash
/usr/bin/python3 - "$OLD" <<'PY'
import hashlib, json, sys
from pathlib import Path
old = Path(sys.argv[1])
m = json.loads(Path('release.json').read_text())
assert m['version'] == 'v0.1.0-rc.15'
assert m['distribution']['kind'] == 'deployment-patch'
assert m['distribution']['base_version'] == 'v0.1.0-rc.14'
assert hashlib.sha256((old/'release.json').read_bytes()).hexdigest() == m['distribution']['base_release_sha256']
for name in ['bootstrap.tar.gz', 'checksums.sha256']:
    p = Path(name)
    assert p.stat().st_size == m['artifact_sizes'][name], name
    assert hashlib.sha256(p.read_bytes()).hexdigest() == m['files'][name], name
print('rc15 signed bootstrap and rc14 base identity verified')
PY
tar -xzf bootstrap.tar.gz
cp -a --reflink=auto "$OLD/images" "$NEW/images"
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" package-verify \
  --release "$NEW" --trusted-key "$TRUST"
```

这会本地复制未变化的镜像分片，支持 reflink 的文件系统可减少空间占用。全包校验按新的 rc.15 清单逐文件完成，禁止省略。模型仍使用原有两个本地目录。

如果只保留了 Docker 已导入镜像，没有 rc.14 原始分片，不能用 `docker save` 重新导出冒充相同分片。可以在验证引导包后运行新版 `fetch`，选择另一个全新下载目录。它会从 rc.14 Release 获取未变化的镜像分片，从 rc.15 获取更新文件；这会产生完整镜像下载流量。

## 3. 网络预检

```bash
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" network-plan --config "$SITE"
```

该命令只读检查 Docker 网络、项目归属及所有 IPv4 路由表（包括策略路由）。输出 `conflicts: false` 才继续。若本项目网络有其他项目容器接入，迁移会拒绝操作，不会强制断开对方。

默认三个子网须与公司 LAN、VPN 和其他项目分配协调确认。不要通过删除其他项目网络、修改全局路由或改签名清单消除冲突。

## 4. 准备加密备份密钥

这是用于本项目数据备份的密钥，**不是发布签名私钥**。已有合规备份密钥时直接复用，不重新生成或覆盖。

如需新建，仅在下列目标不存在时执行一次：

```bash
BACKUP_KEY=/etc/c-check/backup-keys/rtx5880.hex
sudo install -d -m 700 /etc/c-check/backup-keys
sudo sh -c 'set -C; umask 077; openssl rand -hex 48 > "$1"' sh "$BACKUP_KEY"
```

妥善保存该密钥的加密离机备份。不得把它或任何私钥粘贴进聊天、工单或公共仓库。

## 5. 选择一种迁移方式

### A. rc.14 已完成安装，服务正常

实例中存在 `state/deployment.json` 且服务健康时，优先使用标准更新：

```bash
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" update \
  --config "$SITE" --release "$NEW" --version v0.1.0-rc.15 \
  --trusted-key "$TRUST" --backup-key "$BACKUP_KEY"
```

流程：排空任务、加密一致性备份、记录恢复日志、仅重建本项目容器和网络、复用原数据与模型、执行安装验收。

### B. rc.14 有部署记录，但旧网络导致服务不可访问

明确接受中断本项目任务后，使用冷迁移：

```bash
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" update \
  --config "$SITE" --release "$NEW" --version v0.1.0-rc.15 \
  --trusted-key "$TRUST" --backup-key "$BACKUP_KEY" \
  --cold-network-migration
```

该模式不依赖旧 API 排空或模型健康检查。它先停止本项目写入者，完成加密冷备，再重建网络。备份失败则不继续拆网络，保留维护状态和恢复日志。不能用此参数绕过归属、网络冲突或数据备份检查。

### C. rc.14 安装尚未完成，没有部署记录

保留实例目录和现有凭据，使用新版安装器重试；已有网络需要迁移时同样要求备份密钥：

```bash
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" install \
  --config "$SITE" --release "$NEW" --version v0.1.0-rc.15 \
  --trusted-key "$TRUST" --backup-key "$BACKUP_KEY" --gpu-access-mode cdi
```

不要通过删除 `deployment.json` 把完整实例伪装成部分安装，也不要删除数据库或密钥重新初始化。

## 6. 中断恢复与最终核验

若迁移过程中断，`state/network-migration.json` 保持 pending，新的 start/install/update 会拒绝继续。执行：

```bash
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" network-recover --config "$SITE"
```

若目标版本尚未提交，会尝试恢复原配方，并保留数据、不自动回写数据库备份；原配方使用自动网段时，地址可能重新分配。若目标版本已提交而仅日志未收尾，会验证目标部署并完成事务，不盲目降级。恢复后保持提交暂停，按输出验证对应版本后再启用。

正常升级完成应显示 READY，然后核对：

```bash
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" status --config "$SITE"
sudo /usr/bin/python3 "$NEW/cli/ccheck.pyz" verify --config "$SITE"
```

确认版本为 rc.15、三个实际网络子网正确、API/GPU 遥测正常、模型可推理、原上传及历史报告可见。原有其他项目的容器和网络不得被修改。

本补丁复用 rc.14 镜像，验证重点是部署工具、实际 Docker 网络重建、恢复和数据保留；历史 GPU 门禁不是本次重新执行的 GPU 测试。目标 RTX5880 仍由真实安装验收确认。
